## ① Before・After機能

### 不具合の原因

公開処理はDjangoの `content.views.project_detail` → `templates/content/project_detail.html` です。Before側のテンプレートincludeに `image` が渡されておらず、装飾用プレースホルダーが常に表示されていました。`InteriorProject` と管理画面にもBefore画像や比較表示設定は存在しませんでした。After側は既存の `featured_image`（「主要圖片」）を参照していました。

`src/pages/works/[slug].astro` はREADME記載の静的デモで、本番CMSの表示処理ではありません。このデモのダミーデータは変更していません。

### 追加・変更した機能

- `InteriorProject.before_image` を追加。既存の共通単一画像ウィジェット、署名付きR2アップロード、権限確認、圧縮、実画像検証を再利用します。保存キーは `projects/before/YYYY/MM/...` です。
- `InteriorProject.show_before_after` を追加。案件ごとに独立して保存します。
- `has_before_after` が「設定ON、Before登録済み、主要画像登録済み」のすべてを満たす場合だけ比較を表示します。
- Afterは引き続き `featured_image` と既存の焦点設定を使用します。重複するAfterフィールドは作成していません。Beforeは中央配置です。
- 比較画像にはBEFORE／AFTERのキャプションと区別できるaltを表示します。
- OFFや片方の未登録時は比較グリッド自体を出力しません。「03. DESIGN THOUGHT」の文章は保ち、文章用の1列レイアウトにします。
- ギャラリー、主要画像、公開状態、案件の並び順には変更を加えていません。
- Beforeの変更・解除で、以前保存した画像ファイルを物理削除しません。既存共通ウィジェットの未保存アップロードの破棄処理はそのままです。

### マイグレーションと既存データ

`0010_interiorproject_before_after` は2フィールドの追加のみです。既存案件では `show_before_after=True`、`before_image=''` になります。以前の比較表示の意図を維持するため、既存案件を一括OFFにはしません。ただし、元々実画像のなかったBeforeのプレースホルダー比較は、今回の要件どおり非表示になります。主要画像、ギャラリー、本文、公開状態は保持します。Before登録後はONの案件で比較が表示されます。

既存の `db.sqlite3` にはマイグレーションを適用していません。移行テストとブラウザ検証は独立したテストDBで実施しました。本番DB、実R2への書込み・削除は実施していません。

### 管理画面での操作方法

1. 「室內設計」から対象案件の編集画面を開きます。
2. 「圖片」の「主要圖片」がAfterとして表示されます。
3. 「Before・After 比較」の「Before 圖片」で画像を選択し、アップロード完了を待ちます。既存画像は同じ欄でプレビューできます。
4. 「顯示 Before・After 比較」をチェックして保存すると、両画像が登録済みの場合に公開ページへ表示されます。チェックを外して保存すると比較だけを非表示にします。
5. 変更は新しいBefore画像を選択して保存します。解除は「移除圖片」を選択して保存します。解除しても保存済みのR2ファイルは残ります。

## ④ Cloudflare R2

### 無料枠の上限と現在の使用量

| 項目 | R2 Standardの月間無料枠 | 無料枠超過時の公表料金（USD） |
| --- | --- | --- |
| ストレージ | 10 GB-month | $0.015 / GB-month |
| Class A | 100万操作 | $4.50 / 100万操作 |
| Class B | 1,000万操作 | $0.36 / 100万操作 |
| R2からの外向き転送 | 無料 | R2自体の外向き転送料なし |

無料枠はStandardのみです。Infrequent Accessには適用されません。GB-monthは請求期間の各日の最大保存量を平均した指標で、瞬間的な使用量や月間アップロード総量とは異なります。請求単位の切上げもあります。連携する別サービスの料金は別途確認が必要です。[Cloudflare公式料金](https://developers.cloudflare.com/r2/pricing/)

**約1.2GBはユーザー申告値で、今回の実測ではありません。** Standardで同程度の使用量が続き、他のバケット利用等を考慮しない場合、ストレージ無料枠内で、継続保存できる追加容量の単純目安は **10−1.2＝約8.8GB** です。月内の過去ピーク、公開用とstaging用の両バケット、同アカウントの他用途を含む実際の請求対象量は未取得なので、請求額ゼロや残容量8.8GBを確定値として扱うことはできません。無料枠は容量のハードストップではありません。R2のバケット保存容量自体に10GBの上限はありません。[Cloudflare公式制限](https://developers.cloudflare.com/r2/platform/limits/)

### ストレージ設定の確認結果

- `config/settings.py` は `AWS_STORAGE_BUCKET_NAME` があれば `storages.backends.s3.S3Storage` を使用し、endpoint、資格情報、公開ドメイン／署名URLを環境変数から読みます。`file_overwrite=False` です。bucket未設定ならローカル `FileSystemStorage` になります。
- `render.yaml` にはR2用環境変数が宣言されていますが、bucket、endpoint、資格情報、staging bucket、公開ドメインは `sync:false` で、Git内に実値はありません。
- この作業環境を読み取った結果は **FileSystemStorage、R2 bucket未設定、staging bucket未設定、SQLite** でした。これはローカルの状態です。本番がローカル保存であることを示すものではありません。
- コードはブラウザ→非公開staging bucket→Django検証→既存保存bucketへ公開用キーを書き込む構成です。Beforeも同じ経路です。新しいバケットやサービスは追加していません。
- コードからストレージクラスを指定していないため、実バケットのStandard／Infrequent Access設定は未確認です。本番の実endpoint、CORS、公開配信、stagingの非公開設定、ライフサイクルも未取得です。
- 利用可能な接続には本番R2の計測手段がなく、容量・操作回数のAPI問い合わせは行っていません。

実測にはCloudflareのR2対象bucketの「Metrics」で請求期間に合わせた保存量と操作数を確認するか、GraphQLの `r2StorageAdaptiveGroups`／`r2OperationsAdaptiveGroups` を利用できます。公開用・staging用の両方とアカウント全体を確認してください。[Cloudflare公式メトリクス](https://developers.cloudflare.com/r2/platform/metrics-analytics/)

### Class A／Class Bが超過する可能性

PUTやLISTはClass A、HEADやGETはClass Bです。本実装の正常完了1画像あたり、通常はブラウザのstaging PUTと公開用PUTで **A約2回**、完了時のHEADとGETで **B約2回** が発生します。これはコード上の見積りで、実測ではありません。さらにプレビュー・公開画像アクセス・管理画面での閲覧・再試行・一覧取得が加算されます。署名URLの生成自体はローカル処理です。

したがって、保存量が1.2GBでもアクセス等により操作回数の無料枠を超える可能性があります。A/Bの実績は不明です。上記単価と区分は[Cloudflare公式料金](https://developers.cloudflare.com/r2/pricing/)を参照してください。

### サイトで設定されている画像容量・枚数制限

以下はリポジトリの既定値です。本番環境変数による上書き値は未取得です。UIのMB表記に対し、アプリの容量計算は1024²バイト（MiB）です。

| 項目 | 商品ギャラリー画像 | 室内設計・主要画像／Before／ギャラリー |
| --- | --- | --- |
| ブラウザで選べる元ファイル | 1枚30MiB以下 | 同じ |
| 処理後／サーバー検証上限 | 1枚20MiB以下 (`PRODUCT_IMAGE_MAX_BYTES`) | 1枚10MiB以下 (`ADMIN_IMAGE_MAX_OUTPUT_BYTES`) |
| 元画像のクライアント検証 | 各辺12,000px以下、32MP以下 | 同じ |
| サーバーで認める実画像 | 各辺8,000px以下、16MP以下 | 同じ |
| 写真のブラウザ縮小 | 長辺2,800px以下、拡大なし | 同じ |
| 形式 | JPG／JPEG、PNG、WebP | 同じ |
| 1回の複数選択 | 10枚まで | ギャラリー10枚まで。主要画像／Beforeは各1枚 |
| 1商品／案件のギャラリー総枚数 | 固定上限なし | 固定上限なし |

空ファイル、拡張子・MIME・実形式不一致、破損画像、過大寸法、アニメーションはサーバー側でも拒否します。SVG、GIF、HEICは対応しません。クライアント側だけの上限を迂回しても、完了時に実バイト列を検証します。

共通の発行制限は管理ユーザーごとに毎時 **60回／200MiB** です。商品・案件・その他の直接アップロード経路で共用し、署名発行時の処理後容量で計上します。毎時区切りの枠で、案件ごとの枚数上限ではありません。署名URLは10分有効です。

ブラウザでは長辺超過や処理後容量超過時にCanvasで再生成し、JPEG quality 0.9／WebP 0.96を指定します。商品はさらにJPEG／WebPが8MiBを超えた場合にも再生成します。PNGは寸法縮小時等に再保存されますが、常に小さくなる保証はありません。上限内で再生成条件に該当しなければ元の圧縮データをそのまま送ります。最後にサーバーがEXIF方向を補正し、メタデータを持たない画像へ再生成します（JPEG／WebP quality 88）。サーバー側のこの経路ではリサイズせず、寸法超過は拒否します。

管理画面以外からモデルに実ファイルを割り当てる既存経路は別設定で、`MAX_IMAGE_UPLOAD_MB=10`、各辺8,000px、`MAX_IMAGE_PIXELS` 既定16MP、リサイズなしです。`render.yaml` と `.env.example` はこの **旧経路の画素上限だけ40MP** を指定しています。直接アップロードの16MP設定とは別です。商品ではこの旧経路でのみ640×640以内のWebPサムネイルを生成します。現行直接アップロードと公開の商品縮小表示は元画像を利用しています。

### アップロード処理の安全性と追加対応が必要な問題

**既存の防御は実装されています。** ファイル全体の無制限readは行わず、最大バイト数+1までに読み込みを制限します。画像ヘッダーの実寸法・形式・フレーム数を確認してから `source.load()` し、Pillowのdecompression bomb警告もエラーにします。完了処理はユーザー行ロックとDBトランザクションを使い、公開先は別UUIDキーです。再エンコード後の容量も再検証します。保存済み画像を通常の管理編集のたびに再ダウンロードすることも避けています。

一方、次の問題／リスクがあります。タスク④の指示に従い、今回これらの上限や処理仕様は変更していません。

1. **サーバーのメモリ不足リスク（優先して追加対応を検討）。** `verify_and_publish_image` は圧縮データ、デコード画像、EXIF補正画像、クリーン画像、色変換画像、出力バッファを処理中に保持します。バイト上限が10MiBでもデコード後メモリはそれより大きくなります。異なるユーザーの同時完了はユーザー単位ロックで直列化されません。`start.sh` は既定2 Gunicorn workerなので、同時処理のメモリを合算して評価する必要があります。

   ローカルmacOS／Python 3.12.14／Django 5.2.17／Pillow 12.3.0で、実際の既存関数を独立プロセスから呼び、R2クライアントをMockにして `resource.getrusage(RUSAGE_SELF).ru_maxrss` を計測しました。外部通信は0です。

   | 入力fixture | 圧縮ファイル容量 | 処理前最大RSS | 処理後最大RSS |
   | --- | --- | --- | --- |
   | 4000×4000 RGBA PNG（16MP） | 70,231 bytes | 50.7MiB | **291.3MiB** |
   | 2800×2800 RGB JPEG（通常のブラウザ縮小後上限） | 123,128 bytes | 50.8MiB | **171.2MiB** |

   これはローカルの1プロセス実測で、本番のRSS・OOM発生実績ではありません。16MPはサーバー許容上限の検証で、通常のブラウザでは長辺2,800pxへ縮小されます。仮に512MiBの環境で16MPを2プロセス同時処理すれば、単純合算約583MiBとなり超過する可能性があります。実環境のメモリ上限・実画像・同時実行数での検証が必要です。

   修正案は、中間Pillow画像のコピーと生存期間の削減、不要バッファの早期解放、全ユーザーで共有する画像処理の同時実行制御です。画素上限の変更は仕様変更になるため、別途判断してください。`MAX_IMAGE_PIXELS=40000000` の旧経路も見直し対象です。

2. **ブラウザのデコード負荷。** 元画像の寸法は `createImageBitmap`／Imageでデコードした後にチェックします。また、10枚の選択時に `prepare()` を並列開始し、上限2のキューはアップロードにだけ適用されます。巨大画像はブラウザ側で大きなメモリを消費する可能性があります。これはコード上のリスクで、クラッシュの実測ではありません。ヘッダーの寸法確認後にデコードする処理や、最適化キューの同時数制限が改善案です。

3. **公開用ファイルの保持による増加。** 既存の単一画像フォームでは保存済み画像の置換・解除時にファイルを削除しません。今回も要件どおり保持するため、DBで参照しなくなった画像もストレージ容量を消費します。stagingの `pending/` 期限切れルールは既存構成で必要ですが、実設定は未確認です。削除や新しい清掃処理は実施していません。将来必要なら、バックアップと全参照の確認を伴う別の管理作業として検討してください。
